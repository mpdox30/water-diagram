# ADR-005: Backend Service สำหรับรัน Engine แบบ On-Demand (เลือกตำบลจากหน้าเว็บ)

**Status:** Proposed
**Date:** 2026-08-30
**Deciders:** Ton

## บริบท (Context)

ตาม ADR-001 สถาปัตยกรรมปัจจุบันเป็น static site (GitHub Pages) + Supabase ล้วน ๆ ไม่มี backend/server ของ
ตัวเอง — engine (01_data_ingestion.py → 02_topology_graph.py → ... → 04_export_frontend_data.py) เป็น
Python pipeline ที่ต้องรันด้วยมือบนเครื่อง (หรือ cloud sandbox ที่มีข้อจำกัดเครือข่ายบางส่วน) แล้วค่อย publish
ผลลัพธ์เข้า Supabase

Ton ต้องการเพิ่ม UI ในหน้าเว็บ (ใต้หัวข้อ "เครื่องมือจัดการผังน้ำ") ให้ **เลือกตำบลได้จากหน้าเว็บโดยตรง** แล้ว
ให้ engine รันอัตโนมัติเพื่อแกะโครงข่ายน้ำของตำบลนั้นมาแสดงให้แก้ไขทันที — นี่คือการรัน Python pipeline แบบ
on-demand จาก request ของผู้ใช้ ซึ่ง **ทำไม่ได้ด้วย static site เพียงอย่างเดียว** (GitHub Pages serve ไฟล์
static เท่านั้น ไม่มีที่รันโค้ด server-side) และ Supabase เองก็ไม่เหมาะจะรัน pipeline ที่ใช้ geopandas/shapely/
PySheds ซึ่งเป็นไลบรารีหนักและใช้เวลาประมวลผลนานกว่าที่ Edge Function ทั่วไปรองรับ

จึงจำเป็นต้องมี "ที่รันโค้ด Python จริง ๆ" เพิ่มเข้ามาในสถาปัตยกรรม — คำถามคือใช้อะไร โดย Ton เสนอ
**Render** (Render.com) มาเป็นตัวเลือก

## ข้อมูลที่ตรวจสอบ (ราคา/ข้อจำกัดปัจจุบันของ Render, สิงหาคม 2026)

- มี free tier สำหรับ web service จริง: 512 MB RAM, 0.1 CPU, build 500 นาที/เดือน, bandwidth 100 GB/เดือน
- **ข้อจำกัดสำคัญ**: web service บน free tier จะ "spin down" (พักการทำงาน) หลังไม่มี request เข้ามา 15 นาที
  พอมี request ใหม่เข้ามาตอนเครื่อง sleep อยู่ จะต้องรอ **cold start ประมาณ 30-60 วินาที** ก่อนตอบกลับ
- Paid tier ที่เล็กที่สุดที่ไม่ sleep เลย: **$7/เดือน** (0.5 CPU, 512 MB RAM) ถ้าต้องการตอบสนองทันทีทุกครั้ง

## การตัดสินใจ (Decision)

**ใช้ Render เป็น backend service เพิ่มเข้ามา 1 ตัว เฉพาะสำหรับรัน engine แบบ on-demand** — ส่วนที่เหลือของ
สถาปัตยกรรม (static site บน GitHub Pages, Supabase เป็น DB) **ไม่เปลี่ยนแปลง** ยังเป็นไปตามหลักการ ADR-001
(ต้นทุน/ความซับซ้อนต่ำสุด) เกือบทั้งหมด เพิ่มมาแค่ชิ้นเดียวที่จำเป็นจริง ๆ เท่านั้น

**เริ่มที่ free tier ก่อน** เพราะการรัน engine ต่อ 1 ครั้ง (ตอนเลือกตำบลใหม่) เป็นการกระทำที่ผู้ใช้ทำไม่บ่อย
(ไม่ใช่ทุกวินาทีแบบ API ทั่วไป) การรอ 30-60 วินาทีตอนเครื่อง sleep อยู่ (ซึ่งน่าจะเกิดขึ้นบ่อย เพราะการใช้งาน
ห่าง ๆ กัน) ยอมรับได้ในเชิง UX ถ้าแสดง progress/loading indicator ที่ชัดเจนในหน้าเว็บระหว่างรอ — ถ้าใช้งาน
บ่อยขึ้นหรือ Ton ต้องการให้ตอบสนองเร็วเสมอ ค่อยอัปเกรดเป็น paid tier $7/เดือนภายหลังได้ทันที (Render ไม่ต้อง
ย้ายข้อมูล/เปลี่ยนโค้ด แค่เปลี่ยน plan)

## ทางเลือกที่พิจารณา (Options Considered)

### Option A: Render Web Service (เลือก)
| มิติ | การประเมิน |
|---|---|
| ความซับซ้อนในการตั้งค่า | ต่ำ — deploy จาก GitHub repo ได้ตรง ๆ รองรับ Python/Docker native |
| ต้นทุน | ฟรีเริ่มต้น ($0), อัปเกรด $7/เดือนถ้าต้องการ always-on |
| ความสอดคล้องกับสถาปัตยกรรมเดิม | สูง — เพิ่มแค่ 1 ชิ้น ส่วนอื่นเดิมหมด |
| จุดอ่อน | Cold start 30-60 วิบน free tier |

### Option B: Google Cloud Run
| มิติ | การประเมิน |
|---|---|
| ความซับซ้อนในการตั้งค่า | สูงกว่า — ต้องตั้ง GCP project, billing account, IAM |
| ต้นทุน | Pay-per-request จริง ๆ (อาจถูกกว่าถ้าใช้น้อยมาก) แต่ต้องผูกบัตรเครดิตตั้งแต่แรก |
| จุดอ่อน | ซับซ้อนเกินความจำเป็นสำหรับ workload ขนาดเล็กแบบนี้ |

### Option C: ไม่ทำ (คงไว้แบบต้องรันมือ)
| มิติ | การประเมิน |
|---|---|
| ต้นทุน | $0 |
| จุดอ่อน | ไม่ตอบโจทย์ที่ Ton ต้องการ (เลือกตำบลจากหน้าเว็บแล้วรันอัตโนมัติ) |

## ผลที่ตามมา (Consequences)

- ต้องสร้างบัญชี Render และเชื่อมกับ GitHub repo ของโปรเจกต์ (Ton เป็นคนสร้างบัญชี/ผูกบัตรถ้าจะอัปเกรด —
  ทีมพัฒนาช่วยตั้งค่า deploy config ให้)
- ต้องห่อ engine pipeline เป็น API endpoint (เช่น FastAPI/Flask 1 endpoint: รับ tambon → รัน pipeline →
  publish ผลเข้า `nw.save_diagram` แบบ `source='engine'` โดยตรง → ตอบกลับสถานะ/ผลลัพธ์)
- หน้าเว็บต้องมี loading state ระหว่างรอ engine ทำงาน (อาจใช้เวลาหลักสิบวินาทีถึงเป็นนาทีต่อตำบล ขึ้นกับขนาด
  ข้อมูล + cold start)
- ต้องตัดสินใจเรื่อง auth ของ endpoint นี้ (ไม่ควรเปิดให้ใครก็เรียกได้อิสระ เพราะรัน pipeline หนัก) — แนะนำผูก
  กับรหัส manager_tab ที่มีอยู่แล้วในระบบ (ตาม pattern เดียวกับ villager_form) หรือจำกัดเฉพาะทีมพัฒนาเรียกในช่วง
  แรก แล้วค่อยเปิดให้ผู้ใช้ทั่วไปทีหลังถ้าเสถียรดี
- ยังไม่รวมงาน OSM+mitrearth comparison และ DEM/PySheds analysis ไว้ใน endpoint นี้ในรอบแรก — เพิ่มเป็นขั้น
  ต่อไปได้หลังโครงพื้นฐาน (เลือกตำบล → รัน engine → publish) ทำงานเสถียรแล้ว
